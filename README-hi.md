## समस्याएं

Andrej की पोस्ट से:

> "मॉडल्स आपकी ओर से गलत धारणाएं (wrong assumptions) बना लेते हैं और बिना जांचे उनके साथ आगे बढ़ जाते हैं। वे अपने कन्फ्यूजन को मैनेज नहीं करते, स्पष्टीकरण (clarifications) नहीं मांगते, विसंगतियों (inconsistencies) को सामने नहीं लाते, ट्रेड-ऑफ (tradeoffs) पेश नहीं करते, और जब उन्हें पीछे हटना या असहमति जतानी (push back) चाहिए, तब वे ऐसा नहीं करते।"

> "वे कोड और APIs को बहुत अधिक जटिल (overcomplicate) बनाना, एब्स्ट्रैक्शंस (abstractions) को बढ़ाना पसंद करते हैं, डेड कोड को साफ नहीं करते... जहां 100 लाइनों से काम चल सकता है वहां 1000 से अधिक लाइनों का एक भारी-भरकम कंस्ट्रक्शन लागू कर देते हैं।"

> "वे अभी भी कभी-कभी साइड इफेक्ट्स के रूप में उन कमेंट्स और कोड को बदल देते हैं/हटा देते हैं जिन्हें वे पर्याप्त रूप से नहीं समझते हैं, भले ही वे टास्क से पूरी तरह अलग (orthogonal) क्यों न हों।"

## समाधान

एक ही फाइल में चार सिद्धांत (principles) जो सीधे इन समस्याओं का समाधान करते हैं:

| सिद्धांत (Principle) | समाधान (Addresses) |
| --- | --- |
| **Think Before Coding** | गलत धारणाएं (Wrong assumptions), छिपा हुआ कन्फ्यूजन, छूटे हुए ट्रेड-ऑफ (tradeoffs) |
| **Simplicity First** | ओवरकॉम्प्लिकेशन (Overcomplication), भारी-भरकम एब्स्ट्रैक्शंस (bloated abstractions) |
| **Surgical Changes** | ऑर्थोगोनल एडिट्स (Orthogonal edits), उस कोड को छूना जिसे नहीं छूना चाहिए |
| **Goal-Driven Execution** | टेस्ट्स-फर्स्ट (tests-first) और वेरिफिएबल सक्सेस क्राइटेरिया (verifiable success criteria) के माध्यम से लाभ उठाना |

## चारों सिद्धांत विस्तार से

### 1. Think Before Coding

**मानकर न चलें (Don't assume)। कन्फ्यूजन न छिपाएं। ट्रेड-ऑफ को सामने लाएं।**

LLMs अक्सर चुपचाप किसी एक व्याख्या (interpretation) को चुन लेते हैं और उसी के साथ आगे बढ़ जाते हैं। यह सिद्धांत स्पष्ट रूप से सोचने (explicit reasoning) पर मजबूर करता है:

- **धारणाओं को स्पष्ट रूप से बताएं (State assumptions explicitly)** — यदि अनिश्चित हों, तो अनुमान लगाने के बजाय पूछें
- **कई व्याख्याएं (interpretations) पेश करें** — अस्पष्टता (ambiguity) होने पर चुपचाप किसी एक को न चुनें
- **जरूरत पड़ने पर असहमति जताएं (Push back when warranted)** — यदि कोई सरल तरीका मौजूद है, तो वैसा कहें
- **कन्फ्यूज होने पर रुकें** — जो स्पष्ट नहीं है उसे बताएं और स्पष्टीकरण (clarification) मांगें

### 2. Simplicity First

**न्यूनतम कोड जो समस्या का समाधान करे। कुछ भी काल्पनिक या अनुमानित नहीं (Nothing speculative)।**

ओवरइंजीनियरिंग की प्रवृत्ति का मुकाबला करें:

- जितना पूछा गया है, उससे अधिक कोई फीचर्स नहीं
- सिंगल-यूज़ कोड के लिए कोई एब्स्ट्रैक्शंस नहीं
- ऐसी कोई "फ्लेक्सिबिलिटी" या "कॉन्फ़िगरैबिलिटी" नहीं जिसकी मांग न की गई हो
- असंभव परिदृश्यों (impossible scenarios) के लिए कोई एरर हैंडलिंग नहीं
- यदि 200 लाइनों का काम 50 में हो सकता है, तो इसे फिर से लिखें

**टेस्ट:** क्या कोई सीनियर इंजीनियर कहेगा कि यह बहुत जटिल (overcomplicated) है? यदि हाँ, तो इसे सरल बनाएं।

### 3. Surgical Changes

**केवल उसी चीज़ को छुएं जो ज़रूरी है। केवल अपनी फैलाई हुई गंदगी/बदलावों को साफ करें।**

मौजूदा कोड को एडिट करते समय:

- आस-पास के कोड, कमेंट्स या फॉर्मेटिंग को "बेहतर" बनाने की कोशिश न करें
- उन चीज़ों को रीफैक्टर (refactor) न करें जो टूटी या खराब नहीं हैं
- मौजूदा स्टाइल से मेल बिठाएं, भले ही आप इसे अलग तरीके से करते
- यदि आप किसी असंबंधित डेड कोड (dead code) को देखते हैं, तो उसका उल्लेख करें — उसे हटाएं नहीं

जब आपके बदलावों के कारण कुछ कोड अनाथ (orphans) हो जाते हैं:

- उन इम्पॉर्ट्स/वेरिएबल्स/फंक्शंस को हटा दें जो आपके बदलावों के कारण अनुपयोगी (unused) हो गए हैं
- जब तक कहा न जाए, पहले से मौजूद डेड कोड को न हटाएं

**टेस्ट:** प्रत्येक बदली हुई लाइन सीधे यूजर की रिक्वेस्ट से जुड़ी होनी चाहिए।

### 4. Goal-Driven Execution

**सफलता के मानदंड (success criteria) तय करें। सत्यापित (verified) होने तक लूप करें।**

आदेशात्मक कार्यों (imperative tasks) को सत्यापित करने योग्य लक्ष्यों (verifiable goals) में बदलें:

| इसके बजाय... (Instead of...) | इसमें बदलें... (Transform to...) |
| --- | --- |
| "वैलिडेशन जोड़ें" | "इनवैलिड इनपुट्स के लिए टेस्ट लिखें, फिर उन्हें पास कराएं" |
| "बग ठीक करें" | "एक ऐसा test लिखें जो इसे रीप्रोड्यूस (reproduce) करे, फिर उसे पास कराएं" |
| "X को रीफैक्टर करें" | "यह सुनिश्चित करें कि टेस्ट पहले और बाद में पास हों" |

मल्टी-स्टेप टास्क के लिए, एक संक्षिप्त प्लान बताएं:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]

```

मजबूत सक्सेस क्राइटेरिया (Strong success criteria) LLM को स्वतंत्र रूप से लूप करने की अनुमति देते हैं। कमजोर क्राइटेरिया ("इसे काम करने लायक बनाएं") के लिए लगातार स्पष्टीकरण की आवश्यकता होती है।

## इंस्टॉल करें

**विकल्प A: Claude Code प्लगइन (अनुशंसित)**

Claude Code के भीतर से, सबसे पहले मार्केटप्लेस जोड़ें:

```
/plugin marketplace add forrestchang/andrej-karpathy-skills

```

फिर प्लगइन इंस्टॉल करें:

```
/plugin install andrej-karpathy-skills@karpathy-skills

```

यह गाइडलाइन्स को Claude Code प्लगइन के रूप में इंस्टॉल करता है, जिससे यह स्किल आपके सभी प्रोजेक्ट्स में उपलब्ध हो जाती है।

**विकल्प B: CLAUDE.md (प्रति-प्रोजेक्ट)**

नया प्रोजेक्ट:

```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md

```

मौजूदा प्रोजेक्ट (जोड़ने के लिए):

```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md

```

## मुख्य अंतर्दृष्टि (Key Insight)

Andrej की ओर से:

> "LLMs विशिष्ट लक्ष्यों (specific goals) को पूरा करने तक लूप करने में असाधारण रूप से अच्छे होते हैं... उन्हें यह न बताएं कि क्या करना है, उन्हें सक्सेस क्राइटेरिया (सफलता के मानदंड) दें और उन्हें काम करते हुए देखें।"

"Goal-Driven Execution" सिद्धांत इसे कैप्चर करता है: आदेशात्मक निर्देशों को वेरिफिकेशन लूप के साथ घोषणात्मक लक्ष्यों (declarative goals) में बदलें।

## कैसे जानें कि यह काम कर रहा है

ये गाइडलाइन्स काम कर रही हैं यदि आप देखते हैं:

- **डिफ़्स (diffs) में कम अनावश्यक बदलाव** — केवल अनुरोधित (requested) बदलाव ही दिखाई देते हैं
- **ओवरकॉम्प्लिकेशन के कारण कम रीराइट्स (rewrites)** — कोड पहली बार में ही सरल होता है
- **स्पष्टीकरण वाले सवाल इम्प्लीमेंटेशन से पहले आते हैं** — गलतियों के बाद नहीं
- **साफ-सुथरी, मिनिमल PRs** — कोई अनचाहा रीफैक्टरिंग या "सुधार" नहीं

## कस्टमाइज़ेशन

इन गाइडलाइन्स को प्रोजेक्ट-विशिष्ट निर्देशों (project-specific instructions) के साथ मर्ज करने के लिए डिज़ाइन किया गया है। इन्हें अपने मौजूदा `CLAUDE.md` में जोड़ें या एक नया बनाएं।

प्रोजेक्ट-विशिष्ट नियमों के लिए, इस तरह के सेक्शन जोड़ें:

```markdown
## Project-Specific Guidelines

- Use TypeScript strict mode
- All API endpoints must have tests
- Follow the existing error handling patterns in `src/utils/errors.ts`

```

## ट्रेड-ऑफ नोट (Tradeoff Note)

ये गाइडलाइन्स **गति के बजाय सावधानी (caution over speed)** की ओर झुकी हुई हैं। मामूली कामों के लिए (साधारण टाइपो सुधार, स्पष्ट वन-लाइनर्स), अपने विवेक का उपयोग करें — हर बदलाव के लिए पूरी कड़ाई की आवश्यकता नहीं होती है।

इसका उद्देश्य गैर-मामूली (non-trivial) काम पर महंगी गलतियों को कम करना है, न कि सरल कामों को धीमा करना।
