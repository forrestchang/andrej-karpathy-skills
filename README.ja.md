## 問題点

アンドレさんの投稿より：

> 「モデルはあなたに代わって誤った仮定を下し、それを確認することなくそのまま進めてしまいます。自身の混乱を管理せず、明確化を求めず、矛盾を表面化させず、トレードオフを提示せず、本来すべき反論もしません。」

> 「モデルはコードやAPIを過度に複雑にし、抽象化を肥大化させ、不要なコードをクリーンアップしない傾向があります。100行で済むところに、1000行を超える肥大化した構造を実装してしまいます。」

> 「タスクとは直接関係がなくても、十分に理解していないコメントやコードを変更したり削除したりすることがあり、副作用を起こしてしまう場合があります。」

## 解決策

これらの問題に直接対処する、1つのファイルにまとめられた4つの原則：

|原則       |対処する内容|
|-----------|-----------|
|**コーディングの前に思考する**|誤った仮定、潜在的な混乱、トレードオフの欠如
|**シンプルさ優先**           |過度な複雑化、肥大化した抽象化
|**ピンポイントな変更**       |無関係な編集、触れるべきではないコードへの干渉
|**ゴール駆動の実行**         |テスト優先による活用、検証可能な成功基準

## 4つの原則の詳細

### 1. コーディングの前に思考する

**仮定しない。混乱を隠さない。トレードオフを表面化させる。**

LLMはしばしば、黙ったまま一つの解釈を選択し、そのまま実行に移してしまいます。この原則は、明示的な推論を強制するものです。

- **仮定を明示する** — 不確実な場合は、推測せずに質問すること。
- **複数の解釈を提示する** — 曖昧さがある場合、黙って一つを選ばないこと。
- **正当な理由があれば反論する** — よりシンプルな方法がある場合は、そう伝えること。
- **混乱したら立ち止まる** — 不明な点を挙げ、明確化を求めること。

### 2. シンプルさ優先

**問題を解決する最小限のコード。推測によるものは含めない。**

- オーバーエンジニアリングへの傾向を抑制する。
- 要求された以上の機能を追加しない
- 一度しか使わないコードを抽象化しない
- 要求されていない「柔軟性」や「設定のしやすさ」を排除する
- 起こり得ないシナリオに対するエラーハンドリングを行わない
- 200行のコードが50行で済むなら、書き直す

**検証：**  シニアエンジニアならこれは複雑すぎると言うだろうか？もしそうなら、簡素化せよ。

### 3. ピンポイントな変更

**触れるのは必要最低限に。自分が散らかしたものだけを片付ける。**

既存のコードを編集する場合：

- 隣接するコード、コメント、フォーマットを「改善」しない
- 壊れていないものをリファクタリングしない
- 自分のやり方と違っていても、既存のスタイルに合わせる
- 無関係なデッドコード（使用されていないコード）に気づいた場合は、報告のみ行い、削除はしない

変更によって孤立したコード（オーファン）が発生した場合：

- 自分の変更によって不要になったインポート、変数、関数は削除する
- 指示がない限り、以前から存在していたデッドコードは削除しない

**検証：** 変更されたすべての行が、ユーザーの要求に直接結びついていること。

### 4. ゴール駆動の実行

**成功基準の定義と検証ループ**

指令的なタスクを、客観的に検証可能な「ゴール」へと変換します。

| 従来の指示 | 変換後のアクション |
|--------------|-----------------|
| 「バリデーションを追加して」 | 不正な入力に対するテストを書き、それをパスさせる最小限のコードを実装する。 |
| 「バグを直して」 | バグを再現するテストを書き、それがパスする最小限の修正を行う。 |
| 「Xをリファクタリングして」 | 変更前後でテストがパスすることを確認し、機能の同一性を保証する。 |

ステップ数の多いタスクに対しては、作業開始前に以下の形式で簡潔な計画を提示します。

```
1. [手順] → 検証: [確認項目]
2. [手順] → 検証: [確認項目]
3. [手順] → 検証: [確認項目]
```

強力な成功基準があれば、LLMは自律的にループ（検証）を回すことができます。弱い基準（「動かして」など）では、絶え間ない説明が必要になります。

## インストール

**オプションA：Claude Codeプラグイン（推奨）**

Claude Code内から、まずマーケットプレイスを追加してください。
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

その後、プラグインをインストールしてください。
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

これにより、ガイドラインがClaude Codeのプラグインとしてインストールされ、すべてのプロジェクトでそのスキルが利用可能になります。

**オプションB：CLAUDE.md（プロジェクト単位）**

新規プロジェクト:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

既存プロジェクト（追加）:
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Cursorでの使用
このリポジトリには、コミット済みのCursorプロジェクトルール ([`.cursor/rules/karpathy-guidelines.mdc`](.cursor/rules/karpathy-guidelines.mdc)) が含まれているため、Cursorでプロジェクトを開いた際にも同じガイドラインが適用されます。セットアップ方法、他のプロジェクトでのルールの使用方法、およびClaude Codeとの関連性については、**[CURSOR.md](CURSOR.md)** を参照してください。

## 主要な知見

アンジェイさんより:

> "LLMは、特定の目標を達成するまでループを繰り返すことに非常に長けています。何をすべきかを指示するのではなく、成功基準を与えて、その推移を見守ってください。"

「ゴール駆動型実行（Goal-Driven Execution）」の原則は、この本質を捉えています。つまり、命令的な指示を、検証ループを備えた宣言的なゴールへと変換することです。

## 動作確認の方法

以下のような状況が見られれば、これらのガイドラインが機能していると言えます。

- **diff 内の不要な変更の減少** — 依頼された変更のみが反映されるようになります。
- **複雑化による書き直しの減少** — 最初からシンプルなコードが生成されます。
- **実装前の確認質問の増加** — ミスをした後ではなく、作業前に不明点が解消されます。
- **クリーンで最小限のプルリクエスト** — ついでに行われるリファクタリングや、余計な「改善」が含まれなくなります。

## カスタマイズ

これらのガイドラインは、プロジェクト固有の指示と統合して使用するように設計されています。既存の CLAUDE.md に追加するか、新しく作成してください。

プロジェクト固有のルールについては、例えば、以下のようなセクションを追加してください。

```markdown
## プロジェクト固有のガイドライン

- TypeScriptの厳格モード（strict mode）を使用すること
- すべてのAPIエンドポイントにテストを作成すること
- `src/utils/errors.ts` にある既存のエラーハンドリングパターンに従うこと
```

## トレードオフに関する注意点

これらのガイドラインは、スピードよりも慎重さを優先しています。些細なタスク（単純なタイポの修正や、明白な1行の変更など）については、自身の判断に従ってください。すべての変更に対して、常に最大限の厳格さが必要なわけではありません。

目的は、単純な作業のスピードを落とすことではなく、重要度の高い作業においてコストのかかるミスを減らすことです。
