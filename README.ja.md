# Karpathy に着想を得た Claude Code ガイドライン

> 新しいプロジェクト [Multica](https://github.com/multica-ai/multica) をチェックしてください —— コーディングエージェントを実行・管理するためのオープンソースプラットフォームで、再利用可能なスキルに対応しています。
>
> X でフォローしてください: [https://x.com/jiayuan_jy](https://x.com/jiayuan_jy)

[Andrej Karpathy の観察](https://x.com/karpathy/status/2015883857489522876)（LLM コーディングの落とし穴について）をもとにした、Claude Code の挙動を改善するための単一の `CLAUDE.md` ファイルです。

[English](./README.md) | [简体中文](./README.zh.md) | 日本語

## 問題点

Andrej の投稿より:

> 「モデルはあなたに代わって誤った前提を置き、それを確認もせずにそのまま進めてしまう。自分の混乱を管理せず、明確化を求めず、矛盾点を提示せず、トレードオフを示さず、押し返すべきときにも押し返さない。」

> 「コードや API を過度に複雑にし、抽象化を肥大化させ、デッドコードを片付けない傾向が強い……100行で済む実装を1000行の肥大化した構造にしてしまう。」

> 「タスクと直接関係がなくても、十分に理解していないコードやコメントを副作用として変更・削除してしまうことがまだある。」

## 解決策

これらの問題に直接対処する4つの原則を1つのファイルにまとめました:

| 原則 | 対処する問題 |
|-----------|-----------|
| **コーディング前に考える** | 誤った前提、隠れた混乱、トレードオフの欠如 |
| **シンプルさを最優先** | 過度な複雑化、抽象化の肥大化 |
| **外科的な変更** | 無関係な編集、触るべきでないコードへの介入 |
| **ゴール駆動の実行** | テスト先行と検証可能な成功基準によるレバレッジ |

## 4つの原則の詳細

### 1. コーディング前に考える

**推測しない。混乱を隠さない。トレードオフを明示する。**

LLM はしばしば暗黙のうちに1つの解釈を選び、そのまま進めてしまいます。この原則は明示的な推論を強制します:

- **前提を明確に述べる** — 不確かな場合は、推測せずに質問する
- **複数の解釈を提示する** — 曖昧さがある場合、黙って1つを選ばない
- **必要な時は押し返す** — よりシンプルなアプローチがあれば、それを伝える
- **混乱したら止まる** — 何が不明確かを名指しし、明確化を求める

### 2. シンプルさを最優先

**問題を解決する最小限のコード。投機的な要素は一切なし。**

過剰なエンジニアリングへの傾向に対抗します:

- 依頼された以上の機能は追加しない
- 単発利用のコードに抽象化を作らない
- 依頼されていない「柔軟性」や「設定可能性」を加えない
- 起こり得ないシナリオへのエラー処理をしない
- 200行が50行で済むなら、書き直す

**テスト基準:** シニアエンジニアがこれを見て「複雑すぎる」と言うか？もしそうなら簡略化する。

### 3. 外科的な変更

**触れるべきものだけに触れる。自分が作った混乱だけを片付ける。**

既存のコードを編集する際:

- 隣接するコード、コメント、フォーマットを「改善」しない
- 壊れていないものをリファクタリングしない
- 自分ならではのやり方があっても、既存のスタイルに合わせる
- 無関係なデッドコードに気づいたら、指摘はするが削除はしない

自分の変更が孤立したコードを生んだ場合:

- 自分の変更によって使われなくなったインポート・変数・関数は削除する
- 依頼されない限り、既存のデッドコードは削除しない

**テスト基準:** 変更した各行は、ユーザーの依頼に直接たどれるべきである。

### 4. ゴール駆動の実行

**成功基準を定義する。検証されるまでループする。**

命令型のタスクを検証可能なゴールに変換します:

| こう言う代わりに... | こう変換する... |
|--------------|-----------------|
| 「バリデーションを追加して」 | 「無効な入力に対するテストを書き、それを通す」 |
| 「バグを直して」 | 「バグを再現するテストを書き、それを通す」 |
| 「Xをリファクタリングして」 | 「リファクタリング前後でテストが通ることを確認する」 |

複数ステップのタスクでは、簡潔な計画を示します:

```
1. [ステップ] → 検証: [チェック内容]
2. [ステップ] → 検証: [チェック内容]
3. [ステップ] → 検証: [チェック内容]
```

強い成功基準は、LLM が自律的にループできるようにします。弱い基準（「動くようにして」）は絶えず明確化を必要とします。

## インストール

**オプション A: Claude Code プラグイン（推奨）**

Claude Code 内で、まずマーケットプレイスを追加します:
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

次にプラグインをインストールします:
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

これによりガイドラインが Claude Code のプラグインとしてインストールされ、すべてのプロジェクトで利用可能になります。

**オプション B: CLAUDE.md（プロジェクト単位）**

新規プロジェクト:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

既存プロジェクト（追記）:
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Cursor での利用

このリポジトリには、コミット済みの Cursor プロジェクトルール ([`.cursor/rules/karpathy-guidelines.mdc`](.cursor/rules/karpathy-guidelines.mdc)) が含まれており、Cursor でプロジェクトを開いた際にも同じガイドラインが適用されます。セットアップ方法、他のプロジェクトでのルールの使い方、Claude Code との関係については **[CURSOR.md](CURSOR.md)** を参照してください。

## 重要な洞察

Andrej より:

> 「LLM は特定のゴールを達成するまでループするのが非常に得意だ……何をすべきかを指示するのではなく、成功基準を与えて、それがどう動くかを見守るとよい。」

「ゴール駆動の実行」の原則はこれを捉えたものです: 命令的な指示を、検証ループを伴う宣言的なゴールへと変換します。

## うまく機能しているかの見極め方

これらのガイドラインが機能している場合、次のような兆候が見られます:

- **diff 内の不要な変更が減る** —— 依頼された変更のみが現れる
- **過度な複雑化による書き直しが減る** —— コードが最初からシンプル
- **実装前に確認の質問が来る** —— ミスの後ではなく
- **クリーンで最小限の PR** —— 余計なリファクタリングや「改善」がない

## カスタマイズ

このガイドラインは、プロジェクト固有の指示とマージできるように設計されています。既存の `CLAUDE.md` に追加するか、新規作成してください。

プロジェクト固有のルールには、次のようなセクションを追加します:

```markdown
## プロジェクト固有のガイドライン

- TypeScript の strict モードを使用する
- すべての API エンドポイントにテストが必要
- `src/utils/errors.ts` にある既存のエラー処理パターンに従う
```

## トレードオフに関する注記

このガイドラインは**速度よりも慎重さ**を優先する方向に偏っています。些細なタスク（単純なタイプミス修正、明白な1行の変更）については、状況に応じて判断してください —— すべての変更にフルの厳格さが必要なわけではありません。

目的は、非自明な作業における高コストなミスを減らすことであり、単純なタスクを遅くすることではありません。
