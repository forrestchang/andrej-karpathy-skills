# Karpathy に着想を得た Claude Code ガイドライン

> 新しいプロジェクト [Multica](https://github.com/multica-ai/multica) もご覧ください。再利用可能なスキルでコーディングエージェントを実行・管理するためのオープンソースプラットフォームです。
>
> X でフォロー: [https://x.com/jiayuan_jy](https://x.com/jiayuan_jy)

[Andrej Karpathy による LLM コーディングの落とし穴についての指摘](https://x.com/karpathy/status/2015883857489522876)に基づいて、Claude Code の振る舞いを改善するための単一の `CLAUDE.md` ファイルです。

[English](./README.md) | [简体中文](./README.zh.md) | 日本語

## 問題

Andrej の投稿より:

> "モデルは誤った仮定を自分で決めつけ、確認もせずに進めてしまう。自分の混乱を管理せず、確認を求めず、矛盾を表に出さず、トレードオフを示さず、必要なときにも異議を唱えない。"

> "モデルはコードや API を過度に複雑にしがちで、抽象を膨らませ、不要になったコードを掃除しないため、100 行で済むものを 1000 行の肥大化した構造として実装してしまうことがある。"

> "タスクとは無関係でも、十分に理解していないコメントやコードまで変更・削除してしまうことがまだある。"

## 解決策

これらの問題に直接対応する 4 つの原則を、1 つのファイルにまとめています:

| 原則 | 対応する問題 |
|-----------|-----------|
| **コーディング前に考える** | 誤った仮定、隠れた混乱、トレードオフ不足 |
| **シンプルさを最優先** | 過度な複雑化、肥大化した抽象 |
| **外科的に変更する** | 無関係な編集、触るべきでないコードへの変更 |
| **ゴール駆動で実行する** | テスト優先、検証可能な成功基準によるレバレッジ |

## 4 つの原則の詳細

### 1. コーディング前に考える

**仮定しない。混乱を隠さない。トレードオフを示す。**

LLM はしばしば、解釈を黙って 1 つ選び、そのまま進めてしまいます。この原則は明示的な推論を強制します:

- **仮定を明示する** — 不確かな場合は、推測せずに確認する
- **複数の解釈を提示する** — 曖昧さがある場合、黙って選ばない
- **必要なら異議を唱える** — よりシンプルな方法があるなら伝える
- **混乱したら止まる** — 何が不明なのかを言語化し、確認を求める

### 2. シンプルさを最優先

**問題を解決する最小限のコード。推測による追加はしない。**

過剰設計の傾向に対抗します:

- 求められていない機能を追加しない
- 1 回しか使わないコードに抽象を作らない
- 要求されていない「柔軟性」や「設定可能性」を追加しない
- 起こり得ないシナリオのためのエラーハンドリングを追加しない
- 200 行のコードが 50 行で書けるなら、書き直す

**判断基準:** シニアエンジニアが「これは複雑すぎる」と言うか？もしそうなら、シンプルにする。

### 3. 外科的に変更する

**必要な場所だけに触れる。自分が生んだ混乱だけを片付ける。**

既存コードを編集するとき:

- 周辺のコード、コメント、フォーマットを「改善」しない
- 壊れていないものをリファクタリングしない
- 自分の好みと違っても、既存のスタイルに合わせる
- 無関係なデッドコードに気づいたら、言及するだけにする。削除しない

自分の変更によって孤立したコードが生まれたとき:

- 自分の変更で不要になった import、変数、関数を削除する
- もともと存在していたデッドコードは、求められていない限り削除しない

**判断基準:** 変更したすべての行が、ユーザーの依頼に直接結びついていること。

### 4. ゴール駆動で実行する

**成功基準を定義する。検証できるまでループする。**

命令型のタスクを、検証可能なゴールへ変換します:

| こう言われたら... | こう変換する... |
|--------------|-----------------|
| "バリデーションを追加して" | "無効な入力のテストを書き、それを通す" |
| "バグを修正して" | "バグを再現するテストを書き、それを通す" |
| "X をリファクタリングして" | "リファクタリング前後でテストが通ることを確認する" |

複数ステップのタスクでは、短い計画を示します:

```
1. [ステップ] → 検証: [チェック]
2. [ステップ] → 検証: [チェック]
3. [ステップ] → 検証: [チェック]
```

強い成功基準があれば、LLM は自律的にループできます。曖昧な基準（「動くようにして」）では、継続的な確認が必要になります。

## インストール

**選択肢 A: Claude Code プラグイン（推奨）**

Claude Code 内で、まずプラグインマーケットプレイスを追加します:
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

次にプラグインをインストールします:
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

これにより、このガイドラインが Claude Code プラグインとしてインストールされ、すべてのプロジェクトでスキルを利用できるようになります。

**選択肢 B: CLAUDE.md（プロジェクトごと）**

新規プロジェクト:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

既存プロジェクト（追記）:
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Cursor で使う

このリポジトリには、コミット済みの Cursor プロジェクトルール ([`.cursor/rules/karpathy-guidelines.mdc`](.cursor/rules/karpathy-guidelines.mdc)) が含まれているため、Cursor でプロジェクトを開いたときにも同じガイドラインが適用されます。他のプロジェクトでこのルールを使う方法や、Claude Code との関係については **[CURSOR.md](CURSOR.md)** を参照してください。

## 核となる洞察

Andrej より:

> "LLM は、特定のゴールを満たすまでループすることが非常に得意だ……何をするかを指示するのではなく、成功基準を与えて、それが達成されるのを見ればよい。"

「ゴール駆動で実行する」原則は、まさにこの考えを捉えています。命令型の指示を、検証ループを伴う宣言型のゴールへ変換します。

## 効果が出ているサイン

次のような状態が見られれば、このガイドラインは機能しています:

- **diff に不要な変更が少ない** — 依頼された変更だけが現れる
- **過度な複雑化による書き直しが少ない** — 最初からシンプルなコードになる
- **実装前に確認質問が出る** — ミスの後ではなく、事前に確認する
- **クリーンで最小限の PR** — ついでのリファクタリングや「改善」がない

## カスタマイズ

このガイドラインは、プロジェクト固有の指示と統合できるように設計されています。既存の `CLAUDE.md` に追加するか、新しく作成してください。

プロジェクト固有のルールには、次のようなセクションを追加します:

```markdown
## プロジェクト固有のガイドライン

- TypeScript の strict mode を使う
- すべての API エンドポイントにテストを用意する
- `src/utils/errors.ts` にある既存のエラーハンドリングパターンに従う
```

## トレードオフについて

このガイドラインは、**速度より慎重さ**を優先します。単純なタスク（簡単なタイポ修正、明らかな 1 行変更など）では、柔軟に判断してもよい。すべての変更に完全な厳密さが必要なわけではありません。

目的は、非自明な作業でコストの高いミスを減らすことであり、簡単な作業を遅くすることではありません。
